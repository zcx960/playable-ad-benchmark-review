# 可玩广告对比评审方法与规则

## 1. 评审目标

把“初版和竞品看起来不一样”转化为制作人员可以执行、策划可以验收的修改项。评审必须同时覆盖：

- 视觉信息层级：玩家先看什么、能否看懂功能与目标。
- 操作与玩法体验：玩家是否知道怎么做、每步是否有反馈、奖励是否形成闭环。
- 制作执行：改哪个对象、什么时候触发、改成什么状态、参数是多少、如何验收。

## 2. 对比前统一条件

- 两个版本使用相同浏览器、视口尺寸、屏幕方向和静音状态。
- 记录版本链接、测试日期、设备/视口、是否完整跑通。
- 首屏截图必须在相同内容阶段截取；不能把竞品结算画面与初版首屏直接比较。
- 如只拿到截图、视频或静态 HTML，要明确证据范围，不得声称已实测完整玩法。

## 3. 实测顺序

### 3.1 首屏静态检查

按以下顺序记录：

1. 品牌、Logo、CTA、货币栏的位置与安全区。
2. 角色、首个目标、关键设备、资源计数是否一眼可见。
3. 沙地/道路/设备/角色的色相、明度、饱和度和接触阴影。
4. 功能物件是否通过外形、图标、状态表达用途。
5. 是否存在遮挡、裁切、空白过多、多个提示抢注意力。

### 3.2 首次操作

- 记录首次有效输入前显示了什么：操作文案、手势、摇杆、箭头、目标高亮。
- 记录从进入到首次移动、首次采集、首次奖励的触发过程。
- 检查首次有效操作后，教程是否及时消失或切换到下一目标。
- 检查移动死区、最大速度、转向、松手停止、碰撞和可行走入口。

### 3.3 核心因果链

优先按实际产品链路映射，不硬套固定品类：

`输入 → 获取资源 → 携带/存储 → 转化/生产 → 交付/售卖 → 金币/奖励 → 解锁/效率提升`

每个节点回答四个问题：

1. 玩家做了什么？
2. 哪个物件发生了什么可见变化？
3. 数值、实体和音效是否同步？
4. 下一步目标是否立即出现？

### 3.4 反馈节拍

对每次关键动作拆成：

`动作前摇 → 命中/触发 → 受击/状态变化 → 资源生成 → 资源吸附/交付 → 计数变化 → 下一目标`

不能只写“加粒子、加震屏”。必须写清触发帧、持续时长、次数、数量、状态和声音对应关系。

## 4. 视觉评审维度

- **首屏包装**：自有品牌、CTA、货币和玩法主体的层级；不复制竞品商标与素材。
- **构图与镜头**：角色大小、目标位置、留白、道路与功能区的视觉占比。
- **色彩与光照**：地面/设备/角色的色相分离，主光方向，亮暗面一致性。
- **功能可读性**：设备缺料、运行、暂停、满仓、可购买等状态能否不靠说明辨认。
- **模型与阴影**：角色/设备视觉重量、接触阴影、资源与装饰物的区分。
- **UI 与动效**：计数、进度、感叹号、箭头、手势的优先级与切换规则。
- **适配**：至少检查两种竖屏尺寸，核心操作区不得被 Logo、CTA、货币或摇杆遮挡。

## 5. 玩法评审维度

- 首次操作与新手引导。
- 移动手感与目标可达性。
- 采集次数、受击、产出与吸附。
- 背负实体、容量、满仓和交付限制。
- 生产/转化中的投入、启动、运行、暂停原因。
- 交付进度、容器液位/容量、奖励喷出与到账同步。
- NPC/车辆/工人的离场、补位和自动化效率提升。
- 购买价格、扣款进度、解锁行为和下一目标。
- 音效、震动、静音视觉替代。
- 30—60 秒内首次奖励与首次解锁的节奏。

## 6. 反馈写法

每个高优先级问题使用统一结构：

1. **位置/现状**：具体到画面区域、物件、操作阶段；写实际观察，不写猜测。
2. **竞品参考**：说明竞品在哪个阶段、通过什么机制解决；有实测参数就列出。
3. **具体修改**：写对象、触发条件、状态、数量、时长、相对尺寸、切换规则。
4. **验收标准**：用可观察、可复现、可计数的结果描述。

### 好反馈示例

“第三份资源命中后，目标先回弹 0.1 秒，再生成 5 份资源；资源落地 0.2 秒后吸附，0.3 秒飞入背包，每份到账时计数同步缩放一次。验收：关闭计数 UI 仍能凭目标表现判断命中次数与完成状态。”

### 不合格反馈示例

“优化采集手感，加强打击感，让画面更高级。”

## 7. 优先级规则

### P0：本轮必须完成

- 阻碍首次操作或核心循环理解。
- 核心资源“凭空出现/消失”，因果链断裂。
- 首次奖励弱、计数与实体不同步、流程卡死。
- 首屏或小屏下关键 UI 遮挡核心操作。

### P1：尽量本轮完成

- 购买、解锁、补位、音效层级、满仓提示等增强连续体验的内容。
- 明显提升功能可读性和反馈完整度的视觉统一。

### P2：核心稳定后再做

- 新区域、新资源、额外装饰、非关键粒子、外观变体。
- 不能用新增内容掩盖核心循环尚未成立的问题。

## 8. 时间与深挖止损

- 每个版本最多做 2 次完整流程尝试。
- 同一交互卡点最多尝试 3 种合理输入方式；仍失败就记录限制并转向其他可验证证据。
- 默认不因“想再确认一个参数”而长时间反编译或解包。
- 只有关键参数无法从实际体验确认、且会显著影响建议时，才进行源码/资源核对。
- 用户要求加速时，立即停止非必要深挖，用已确认证据完成报告，并标明未验证项。

## 9. 禁止事项

- 不编造已跑通的流程、实测参数、音效、震动或性能表现。
- 不把建议值写成竞品现有值。
- 不用“提升质感、优化体验、加强反馈、更加丝滑”作为完整修改项。
- 不机械照抄竞品 Logo、商标、角色、付费素材或受保护资产。
- 不只列优缺点；必须落到修改和验收。
- 不在同一阶段给玩家多个同等强度的主目标提示。
